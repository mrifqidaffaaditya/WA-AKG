# 🌐 Internationalization (i18n)

WA-AKG's dashboard UI can be shown in several languages. Translations are powered by [`next-intl`](https://next-intl.dev) in its **cookie-based mode**: URLs stay the same (no `/en/...` prefixes) and the REST API is not affected.

## Supported languages

| Code | Language |
| :--- | :--- |
| `en` | English (reference / fallback) |
| `id` | Bahasa Indonesia |
| `pt-BR` | Português (Brasil) |

## How the language is chosen

For every request the server picks the first match from:

1. The **`NEXT_LOCALE` cookie**, set by the language switcher (navbar, mobile menu, login and register pages).
2. The **`DEFAULT_LANGUAGE`** environment variable.
3. **English** (`en`).

Matching is forgiving: `pt-br`, `PT-BR` and `pt` all resolve to `pt-BR`, and `id-ID` resolves to `id`. Unknown values are ignored.

> `DEFAULT_LANGUAGE` only controls the UI language. `LOCALE` and `TZ` keep their current meaning (date formatting and scheduler timezone).

## Project layout

```
src/i18n/
├── config.ts            # Supported locales, cookie name, locale resolution
├── request.ts           # next-intl request config (reads cookie → loads messages)
├── actions.ts           # Server action used by the language switcher
├── global.d.ts          # Type-safe message keys (based on en.json)
├── messages/
│   ├── en.json          # Reference catalog: every key must exist here
│   ├── id.json
│   └── pt-BR.json
└── __tests__/           # `npm test`
src/components/language-switcher.tsx
```

## Using translations in components

```tsx
// Client or server component
import { useTranslations } from "next-intl";

export function Example({ count }: { count: number }) {
    const t = useTranslations("notifications");
    return <p>{t("unreadSummary", { count })}</p>;
}
```

- In async server components, use `getTranslations` from `next-intl/server`.
- Messages use [ICU syntax](https://next-intl.dev/docs/usage/messages): `{name}` placeholders, `{count, plural, one {...} other {...}}`, and rich text such as `<terms>...</terms>` with `t.rich()`.
- Dates and numbers: use `useFormatter()` (for example `format.relativeTime(date, now)`) so they follow the active language.

Keys are **type-checked** against `en.json`: a typo like `t("seeAlll")` fails `npx tsc --noEmit` and `npm run build`.

## Translating a new part of the UI

1. Add the new keys to `src/i18n/messages/en.json`, grouped by feature (e.g. `"broadcast": { ... }`).
2. Add the same keys to **every** other catalog (`id.json`, `pt-BR.json`).
3. Replace the hard-coded strings with `t("...")`.
4. Run `npm test` and `npx tsc --noEmit`.

## Adding a new language

1. Copy `src/i18n/messages/en.json` to `src/i18n/messages/<code>.json` (e.g. `es.json`) and translate the values. Keep keys, `{placeholders}` and `<tags>` unchanged.
2. Register the code in `locales` and its native name in `localeNames` in `src/i18n/config.ts`.
3. Run `npm test`. It fails if a key is missing, empty, or has different placeholders than `en.json`, or if a message has invalid ICU syntax.

## Tests

```bash
npm test
```

They check:

- Every locale in `config.ts` has a catalog file, and the reverse.
- All catalogs have exactly the same keys as `en.json`, with no empty values.
- Placeholders and rich-text tags match `en.json`.
- Every message renders without ICU errors.
- Plural output and the cookie / env / fallback resolution order.
